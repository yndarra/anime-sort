1. Файлы и когда они читаются
-----------------------------
    config.json    общие настройки: какие пачки запускать, пути, подписи этапов, ширины столбцов окна
    configN.json   одна пачка (config1.json, config2.json …): папки и этапы
    live.json      параметры, которые можно менять во время работы

Запуск — двойной щелчок по start.vbs: открывается главное окно anime-sort, оно проверяет конфиги и запускает пачки.
Только проверить, без запуска:  venv\Scripts\python.exe engine\main.py --check

    - config.json и configN.json читаются ТОЛЬКО при запуске. Их копия сохраняется в
      logs\config-snapshots\<время запуска> (последние 50), и пачки работают по этой копии — правки во время
      работы ни на что не влияют и действуют со следующего запуска.
    - Исключение: конфиг, который при запуске был с ошибками. Главное окно ждёт, пока его исправят и сохранят,
      проверяет снова и запускает только эту пачку (остальные работают дальше). Пока с ошибками config.json,
      не запускается ничего; после исправления — всё.
    - live.json читается на ходу: каждое сохранение проверяется, в журнале главного окна пишется, что на что поменялось;
      ошибка — выводится красным, работа идёт со старыми значениями.
    - Ошибки выводятся в журнале главного окна красным (подсказка «Как исправить» — зелёным) и в logs\config_check.txt.


2. Правила записи JSON
----------------------
    - весь файл — объект в фигурных скобках { … };
    - имена параметров и текст — в ДВОЙНЫХ кавычках: "name": "reverse";
    - числа — без кавычек, дробная часть через точку: 0.55;
    - логические значения — true / false маленькими буквами (без кавычек);
    - список — в квадратных скобках: ["data8..30", "data49"];
    - запятая между элементами, но НЕ после последнего перед } или ];
    - пути — с прямыми слэшами: "C:/Users/…" (обратный слэш в JSON служебный, его пришлось бы удваивать);
    - комментариев (# или //) в JSON нет. Вместо них — параметр, имя которого начинается с //:
          "//": "любой текст",   "//paths": "пояснение к путям"
      В списке этапов комментарий — отдельный объект {"//": "текст"}. Такие параметры игнорируются.
    - один параметр в одном объекте — один раз (повтор — ошибка).


3. config.json — общие настройки
--------------------------------
Параметр        Обязательно  Значение
"run"           да           список пачек для запуска: ["config1", "config2"] (без .json). Обычно его пишет prepare.bat
                             вместе с configN.json (из template.json) — вручную править не нужно
"collection"    да           папка коллекции, где лежит anime-paths.json (общий файл путей с проектом anime-vault):
                             из него waifu (итоговая коллекция), batches (исходные dataN — не изменяются, наборы берут
                             копии) и results (куда класть наборы test-dataN). Старые ключи "waifu", "source",
                             "results" (полные пути) ещё понимаются — вместо "collection"
"names"         нет          подписи этапов по id: "AI-K3": ["AI-K3", "AI Kimi K3"]
                               1-е — метка в логе и префикс имён файлов в папках результатов (до 20 символов,
                                     без \ / : * ? " < > |, не «Other», не «ALL», не повторяется у разных этапов);
                               2-е — название в таблице окна (можно не указывать — будет как метка).
                             Этап без строки подписывается своим id.
"log_columns"   нет          ширина столбцов лога (левая часть окна), целые числа 1…300:
                             time 21, stage 7, status 12, file 33, confidence 4, title 50, character 50
"table_columns" нет          ширина столбцов таблицы (правая часть окна): stage 12, determined 10, nd 5,
                             error 6, expected 8, remained 8
"monitor"       нет          на каком мониторе при старте главное окно и окна наборов: номер Windows 1…16 (как в
                             «Параметры → Дисплей → Определить»; главное окно при старте пишет список мониторов).
                             Такого монитора нет — предупреждение, окна на основном. Не указан — основной
Ширина окна подстраивается под сумму столбцов. Свободные ядра и прочее «на ходу» — в live.json, не здесь.


4. configN.json — пачка
-----------------------
{
  "name": "reverse",
  "folders": ["data8..30", "data49"],
  "previous": "drop",
  "stages": [ {…}, {…} ]
}
Параметр     Обязательно  Значение
"name"       да           имя пачки: журнал logs\batch_<name>.log, строки в главном окне. До 40 символов, без \ / : * ? " < > |.
                          У разных конфигов имена должны различаться
"folders"    да           папки из source по порядку прохода. Диапазон "data8..30" — data8, data9 … data30;
                          может идти по убыванию: "data30..8". Можно строкой через запятую: "data8..30, data49".
                          Папка не может встречаться дважды и не может быть в двух запускаемых конфигах сразу
"previous"   нет          "drop" (по умолчанию) — действуют только этапы этого конфига: определения этапов,
                          которых в нём нет, сбрасываются, их папки в out\ удаляются.
                          "keep" — результаты прошлых прогонов набора сохраняются, этапы конфига работают
                          поверх них и нумеруются после уже имеющихся папок (так сделан config2: только N-LR
                          по готовым наборам — «6. N-LR», «7. Other»)
"stages"     да           этапы в порядке работы (раздел 5 и 6)


5. Этапы: общие параметры, from и where
---------------------------------------
{"id": "AI-F5", "type": "ai_image", "api": "bridge/key_new", "model": "claude-fable-5-1",
 "accept": 0.55, "from": 0.20, "where": "[AI-K3]", "enabled": true}

Параметр    Значение
"id"        имя этапа: начинается с латинской буквы, дальше латиница, цифры, - _ &, до 20 символов
            (AI-K3, N-L&R). В одном конфиге не повторяется; один тип можно поставить несколько раз под разными
            id (AI-K3 и AI-K3b с разными api/model). Зарезервированы: PIPELINE, LINE, GUI, SUMMARY, ALL
"type"      тип этапа (раздел 6)
"enabled"   false — этап выключен: не работает, не проверяется, не считается в нумерации папок; по умолчанию true
"accept"    порог принятия, число в (0; 1]: уверенность >= accept — файл определён. Обязателен у wd14, camie,
            ai_image, json_meta; у соседей его нет
"api"       "провайдер/ключ" — папка providers\<провайдер> (там provider.json) и файл ключа <ключ>.txt в ней —
            или СПИСОК таких API по порядку попыток (раздел 8). Только у ai_image и json_meta
"model"     имя модели из "models" файла provider.json. Только у ai_image и json_meta
"failover"  (необязательно) свои пороги переключения API для этого этапа вместо live.json:
            {"errors": 3, "minutes": 5, "recheck_minutes": 20, "quota_recheck_minutes": 120} (любые из них)
"from"      (необязательно) нижняя граница уверенности для входа на этап, число в [0; 1)
"where"     (необязательно) по результатам каких этапов выше отбирать файлы (ниже)

Какие файлы идут на этап
    - только ещё не определённые, не проверенные этим этапом и не битые;
    - файл, упавший с ошибкой на одном из этапов выше, ждёт повтора того этапа и дальше не идёт;
    - первый этап берёт все файлы (from/where у него игнорируются — предупреждение);
    - нет ни from, ни where — все не определённые файлы;
    - from без where — уверенность «опорного» этапа >= from. Опорный — последний этап выше с уверенностью
      (wd14, camie, ai_image, json_meta), который реально проверял этот файл;
    - where — выражение из [ЭТАП], and, or и скобок. [X] выполнено, если этап X проверял файл, не определил его
      и уверенность X была >= from этого этапа (from не указан — 0):
          "where": "[AI-F5] and [AI-K3]"             оба условия
          "where": "[AI-K3] or [AI-F5] or [AI-G6]"   хотя бы одно
          "where": "([AI-K3] or [AI-F5]) and [Camie]"
      Можно ссылаться только на включённые этапы ВЫШЕ этого, дающие уверенность (не на соседей). and/or можно
      писать и как и/или, &&/||. Отрицания (not) нет.
    Сверху диапазон ограничен порогом этапа сам собой: выше порога файл уже определён. Ответ, который этап
    отклонил несмотря на высокую уверенность (несколько тайтлов, нет персонажа), тоже идёт дальше.


6. Типы этапов
--------------
wd14 — локальный теггер WD-14 (EVA02-Large), без интернета
    Параметры: accept (обязателен) — порог character-тегов; from, where.
    Определяет, если теги выше порога дают одного персонажа (тайтл + персонаж) или нескольких персонажей
    одного тайтла (только тайтл). Персонажи разных тайтлов — не определено. Работает на ядрах, не занятых
    free_cores (live.json).

camie — локальный теггер Camie (новее словарь персонажей). Всё как у wd14.

ai_image — модель смотрит на картинку (текст пина идёт подсказкой)
    Параметры: api, model, accept — обязательны; from, where.
    Определяет, если модель назвала и тайтл, и персонажа, тайтл один и уверенность >= accept.
    Ответы кэшируются в cache\ набора: повторный запуск, снижение accept или второй этап с той же моделью
    (AI-K3b) запросов не тратят.

json_meta — модель читает только текст пина, встроенный в файл (metadata), без картинки
    Параметры: api, model, accept — обязательны; from, where. Идут только файлы, у которых есть metadata.
    Определяет, если ответ подтверждается самим текстом metadata (и каталогом tools\ani\ani.txt) и
    уверенность >= accept. Может определить только тайтл.

Соседи — определяют по соседним файлам (по порядку сохранения), без моделей. Параметров accept, api, model нет;
from и where можно. Учитываются определения, сделанные ДО начала этапа (этапами выше), поэтому определение
не «протягивается» по цепочке из нескольких файлов. Все соседи определяют только ТАЙТЛ (файл кладётся в папку
тайтла, без папки персонажа).

    neighbors (N)          ближайшие определённые файлы слева И справа — один тайтл И один персонаж
    neighbors_title (N-L&R) ближайшие определённые файлы слева И справа — один тайтл (персонажи любые)
    neighbors_left (N-L)   непосредственный сосед СЛЕВА определён — его тайтл
    neighbors_right (N-R)  непосредственный сосед СПРАВА определён — его тайтл
    neighbors_lr (N-LR)    непосредственный сосед слева ИЛИ справа определён — его тайтл; определены оба и тайтлы
                           разные — тайтл ЛЕВОГО
    neighbors_rl (N-RL)    то же, но при разных тайтлах — тайтл ПРАВОГО

    Разница «ближайший определённый» (N, N-L&R) и «непосредственный сосед» (N-L, N-R, N-LR, N-RL): первые
    ищут определённые файлы в обе стороны сколь угодно далеко, вторые смотрят только на соседний файл.
    Пример (A, B — тайтлы, - — не определён):  A  -  -  -  A  -  B
        N-L&R: три «-» между A и A получают A; «-» между A и B — нет (тайтлы разные).
        N-LR:  первый «-» получает A (сосед слева), третий — A (сосед справа), средний остаётся не определён
               (оба его соседа не определены); «-» между A и B получает A (при разных тайтлах — левый).

Сейчас в config1: … JSON → N-L&R → N-LR; N, N-L, N-R, N-RL выключены ("enabled": false).


7. live.json — параметры на ходу
--------------------------------
Параметр                Умолч.  Диапазон  Значение
"free_cores"            2       0…ядер-1  сколько ядер процессора оставлять свободными (0 — занимать все).
                                          Локальные теггеры всех пачек вместе работают только на остальных;
                                          меняется сразу, перед следующим файлом
"memory_wait_seconds"   60      5…3600    не хватило оперативной памяти — пауза перед повтором того же файла
"memory_retries"        30      1…1000    сколько раз подряд ждать память, прежде чем считать это ошибкой файла
"crash_retries"         2       0…20      сколько раз сразу перезапускать набор после аварийного падения
"broken_after_runs"     3       1…50      после скольких неудачных запусков этапа файл считается битым
"broken_after_crashes"  2       1…20      после скольких падений процесса на файле он считается битым
"failover_errors"       5       1…100     сбоев API подряд до перехода к следующему API этапа
"failover_minutes"      10      1…1440    минут сбоев без единого успеха до перехода к следующему API
"failover_recheck_minutes"        20  1…1440   сколько минут «спит» упавший API до повторной проверки
"failover_quota_recheck_minutes"  120 1…10080  через сколько минут проверить API с исчерпанным балансом
Все значения — целые числа без кавычек. Параметр можно не указывать — будет значение по умолчанию.

Окна (главное и окна наборов) — тоже в live.json, но применяются НЕ на ходу: главное окно берёт их при старте
(сетап 1, режим 1 — для себя и всех новых окон), дальше — только кнопками главного окна («Сетап 1/2/3»,
«Режим 1/2», «Монитор ›»); в момент нажатия live.json перечитывается.
Правка видна в журнале строкой «live.json, окна (применится кнопкой в главном окне): …».
"arrangements"   две расстановки: "arrangements": {"1": {"mode": …, "margin": …, "gap": …}, "2": {…}}, кнопки «Режим 1/2»:
    "mode"         "left-right" — слева сверху вниз, пока окна влезают по высоте, потом справа сверху вниз, потом
                   снова слева поверх; "center" — посередине сверху вниз, потом снова сверху поверх.
                   Порядок — по времени открытия, главное окно первое. Кнопка ставит все окна на монитор, где её нажали;
                   туда же и по тому же режиму открываются следующие окна
    "margin"       0…300 пикселей: отступ от краёв экрана (без панели задач)
    "gap"          0…300 пикселей: отступ между соседними окнами
    По умолчанию: 1 — left-right, 2 — center, от краёв 20, между окнами 10.
    Монитор при старте — "monitor" в config.json (номер Windows; такого нет — основной); главное окно при старте
    пишет список мониторов с номерами и размерами.
"setups"         три сетапа:   "setups": {"1": {...}, "2": {...}, "3": {...}}, у каждого все пять параметров:
    "width"        размер всего окна с заголовком: пиксели 300…8000, проценты от ширины экрана строкой ("49%")
                   или "auto" — по ширине столбцов лога и таблицы (log_columns/table_columns) при этом шрифте
    "height"       пиксели 120…5000 или проценты от высоты экрана без панели задач ("23%")
    "table_width"  правая часть с таблицей: пиксели 150…4000, проценты от ширины окна ("26%") или "auto"
    "log_font"     размер шрифта лога, пункты 6…30
    "table_font"   размер шрифта таблицы, пункты 6…30
    Сетап 1 по умолчанию — размеры окон до появления сетапов: 1802×332, таблица 436, шрифт 9.
    Общее состояние окон — logs\windows.json (engine\winlayout.py).


8. Провайдеры (providers\<имя>\provider.json) и несколько API на этап
----------------------------------------------------------------------
provider.json:
"endpoint"     адрес https://…/v1/chat/completions (формат OpenAI)       обязательно
"auth"         "Bearer" (другое не поддерживается)                        по умолчанию "Bearer"
"reasoning"    бюджет рассуждений Claude-моделей: "anthropic" (мост), "openrouter" или "none"
"interval"     секунд между запросами, 0…120                              по умолчанию 3.2
"models"       {"имя в конфиге": "имя модели у провайдера"}               обязательно
"images"       false — провайдер не принимает картинки (только json_meta)  по умолчанию true
"temperature"  false — не отправлять temperature (шлюз отвечает на него ошибкой)   по умолчанию true
Ключ — отдельный файл <ключ>.txt в той же папке, одной строкой. Подробнее — providers\README.txt.

Несколько API на этап — "api" списком, порядок = порядок попыток:
    {"id": "AI-GF", "type": "ai_image", "model": "gemini-3.8-flash", "accept": 0.80,
     "api": ["beniclo/key1", "ritttta/key1", "beniclo/key0"]}
    Элемент — "провайдер/ключ" или объект с другой моделью для этого API: {"api": "ritttta/key3", "model": "gpt-6-sol"}.
    Модель у этапа одна (accept подобран под неё): у ai_image объект с другой моделью — предупреждение;
    у json_meta — нормально (определение подтверждает сам текст пина).
    Проверка: модель должна быть в "models" провайдера; файла ключа нет или он пустой — этот API пропускается
    (предупреждение), ошибка — только если ключа нет ни у одного API этапа; один API дважды — ошибка;
    провайдер с "images": false в ai_image — ошибка.

Как этап переключается:
    - работает первый API списка, который не «спит» и у которого есть ключ (файл ключа перечитывается —
      вписанный на ходу ключ подхватывается без перезапуска);
    - баланс ключа исчерпан (HTTP 402, или 400/401/403 со словами insufficient/quota/balance/credit) — API сразу
      засыпает на failover_quota_recheck_minutes, тот же файл уходит в следующий API;
    - failover_errors запросов подряд кончились ошибкой (уже после внутренних повторов: сеть, 5xx, тайм-аут, 429,
      пустой/неразборчивый ответ, ответ потоком SSE) или ошибки идут дольше failover_minutes без единого успеха —
      API засыпает на failover_recheck_minutes, файл уходит в следующий (для файла это не ошибка);
    - сон истёк — API проверяется одним запросом: успех — он снова текущий (стоящий выше по списку — главнее),
      неудача — снова спит;
    - спят все — этап ждёт ближайшего пробуждения («все API этапа … недоступны, повтор в HH:MM» в окне и консоли);
      файлы при этом не засчитываются как битые.
    Каждое переключение — строка в окне набора и в главном окне с причиной; текущий API — под таблицей окна.
    Кэш ответов — по модели, а не по API: переключение ключа и перезапуск набора не переспрашивают.


9. Битые файлы
--------------
Файл помечается битым, если: не открывается как картинка (пустой/повреждённый jpg, png, webp, gif) — сразу;
этап не смог его обработать в broken_after_runs запусках (сбой сервиса — сеть, HTTP, неразборчивый ответ —
засчитывается, только если в том же запуске этап справился с другими файлами); процесс конвейера падал на нём
broken_after_crashes раз (нехватка памяти не считается). Битый файл дальше не обрабатывается, остаётся в «Other»
и не мешает набору завершиться; об этом — красная строка в окне набора и в главном окне, список с причинами —
results\test-dataN\out\broken.txt. Пометка снимается сама, если заменить файл нормальной копией в исходной dataN.


10. Что происходит при изменении конфигов
-----------------------------------------
    - Завершённый набор, для которого изменились этапы (добавлен/выключен этап, другие from/where/модель/порог),
      при следующем запуске открывается снова: состояние берётся из итогового снапшота, работают только этапы,
      которые файлы ещё не проходили (ответы моделей — из кэша набора).
    - Этап убран или выключен ("previous": "drop") — его определения перестают действовать: такие файлы снова не
      определены и идут по этапам конфига, папка этапа в out\ удаляется. Вернёте этап — определит их заново.
    - Уже проверенные этапом файлы не перепроверяются. Исключение — снижение accept у ai_image: файлы, чей
      сохранённый ответ теперь проходит порог, пересматриваются (из кэша, без новых запросов).
    - Порядок или метки этапов изменились — папки результатов переименовываются под новую нумерацию.


11. Ошибки проверки: причины и как исправить
--------------------------------------------
Каждая ошибка показывает файл и строку. Частые случаи:

Синтаксис JSON (любой файл)
    «в конце строки не хватает запятой»            пропущена запятая после значения на этой строке
    «здесь ожидается значение»                     лишняя запятая перед ] или }, пропущено значение или текст
                                                   без кавычек
    «ожидается имя параметра в двойных кавычках»   лишняя запятая перед }, одинарные кавычки, имя без кавычек
    «строки в JSON пишутся в двойных кавычках»     'текст' вместо "текст"
    «обратный слэш \ в строке JSON — служебный»    путь "C:\Users\…" — пишите "C:/Users/…"
    «логические значения … маленькими буквами»     True/False/None вместо true/false/null
    «в JSON нет комментариев через # или //»       строка-комментарий — замените на "//": "текст"
    «дробная часть числа через запятую»            0,55 вместо 0.55
    «строка не закрыта кавычкой», «после конца конфига есть ещё текст», «файл пустой», «не в кодировке UTF-8»
    «параметр … указан второй раз»                 один и тот же параметр дважды в одном объекте

config.json
    «неизвестный параметр …» (с подсказкой «Возможно, вы имели в виду …»)   опечатка или параметр не из этого файла
                                                   (free_cores — в live.json)
    «не указан run» / «run пустой» / «указан дважды» / «в run указан сам config.json или live.json»
    «конфиг … не найден (нет файла configs\….json)» имя в run не совпадает с файлом
    «waifu/source: папки … нет», «путь … не полный», «results: нет ни папки, ни папки над ней»
    «метка … содержит символы / длиннее 20 символов / совпадает со служебной папкой / уже занята этапом …»
    «log_columns → stage = 7.5: ширина — целое число», «неизвестный столбец …», «вне диапазона [1; 300]»

configN.json
    «не указано name / folders», «name … не годится для имени файла журнала»
    «folders: диапазон … записан неверно»          пишется "data8..30"
    «folders: «12» — нужно имя папки»               пишите "data12"
    «folders: папки указаны больше одного раза»     пересекающиеся диапазоны
    «folders: в … нет папок: …» / «в папках нет картинок»
    «previous … — непонятное значение»              только "keep" или "drop"
    «нет списка этапов stages» / «все этапы выключены»
    «папки … уже проходит configM.json»            одна папка в двух запускаемых конфигах
    «name … уже у configM.json»                    одинаковые имена пачек

Этапы
    «у этапа №… не указан id», «имя этапа … не годится», «зарезервировано», «этап … уже есть (строка …)»
    «не указан type» / «неизвестный type …» (с подсказкой и списком типов)
    «не указан accept» (обязателен у wd14/camie/ai_image/json_meta), «accept … вне диапазона (0; 1]»
    «у этапа neighbors… нет порога принятия (accept)» / «этапу … не нужен api/model» — у соседей их нет
    «неизвестный параметр …»                        опечатка (acept, form …)
    «число "0.55" записано в кавычках», «… — не число», «enabled: … — нужно true или false»
    «from … вне диапазона [0; 1)»
    «from: выше нет ни одного этапа с уверенностью» — from у этапа, над которым только соседи
    «from = … не меньше порогов всех этапов выше — сюда не попадёт ни один файл»
    «первый этап — from/where игнорируются» (предупреждение)
    «метка … совпадает с меткой этапа …»           две метки одинаковые (names в config.json)

where
    «между этапами нет and/or», «не закрыта скобка (», «лишняя закрывающая скобка )», «выражение обрывается»,
    «пустые скобки []», «… — не этап в квадратных скобках и не and/or», «отрицание (not) не поддерживается»
    «этап [X] идёт ниже этого»                     ссылаться можно только на этапы выше
    «этапа [X] нет в этом конфиге (или он выключен)»
    «where ссылается на сам этап»
    «этап [X] (neighbors…) не даёт уверенности»    в where — только wd14, camie, ai_image, json_meta
    «from = … не меньше порога [X]»                через [X] сюда не попадёт ни один файл

api / model / провайдер
    «api — пустой список», «api — 5: нужна строка «провайдер/ключ» или объект», «в элементе api лишние параметры»
    «API … указан в списке дважды»
    «провайдер … не принимает картинки ("images": false)» — текстовый провайдер в ai_image
    «у API … другая модель, а accept подбирался под …» (предупреждение, ai_image)
    «ключей пока нет, эти API пропускаются: …» (предупреждение) / «ни у одного API этапа нет ключа» (ошибка)
    «failover: неизвестный параметр …», «failover → errors … вне диапазона», «этапу wd14 не нужен failover»
    «api …: нужно «провайдер/ключ» — ровно две части»
    «провайдер … не найден (нет папки providers\…)», «нет файла providers\…\provider.json»
    «файла ключа … нет. Возможно, вы имели в виду …» (опечатка в имени), «не похоже на ключ»
    «модели … нет в provider.json» (с подсказкой и списком моделей) — добавьте её в "models"
    provider.json: «не указан endpoint», «endpoint … не похож на адрес», «reasoning … неизвестен»,
    «auth … не поддерживается», «нет списка моделей models», «модель …: пустая строка»,
    «images/temperature: … — нужно true или false»

live.json
    «… вне диапазона …»                            например free_cores больше числа ядер - 1
    «… — нужно целое число без кавычек»            "60", 2.5 и т.п.
    «неизвестный параметр …»                       опечатка в имени
    При ошибке работа продолжается со старыми значениями.
